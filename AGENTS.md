# AGENTS.md

Django 6.0.7 app (Python 3.14, PostgreSQL, ASGI/uvicorn) for production batches and "Chestny Znak" marking codes. DRF + drf-spectacular, `django-tasks-db` background workers. All UI text and model `verbose_name`s are Russian.

`README.md` is the product description; this file is the agent-facing gotcha sheet. `docs/` is derived prose (partly stale) — the code, README and this file win.

## Quick commands

```bash
# Windows: dependencies exist only in .venv (system python has no Django)
.venv\Scripts\Activate.ps1          # or call .venv\Scripts\python.exe

python run_all.py                   # web + scheduler + worker in one terminal
uvicorn config.asgi:application --host 0.0.0.0 --port 8888
python manage.py run_scheduler      # --once = enqueue every task once and exit
python manage.py run_tasks_worker

python manage.py makemigrations <app_label>
python manage.py migrate                       # also: --database archive
python manage.py test app_uip app_cz app_factory app_event app_scheduler app_page app_helper
python manage.py test app_uip.tests.ReserveAccumulationTests.test_generate_count_loops
```

- Fresh checkout: `pip install -r requirements.txt`, **then** `pip install -e .`. `pyproject.toml` declares no dependencies, and `-e` generates `config/_version.py` (setuptools-scm).
- `run_all.py` binds uvicorn to the machine's LAN IP and adds `--reload` unless `DEBUG` is explicitly `0`. Only uvicorn reloads — restart `run_scheduler`/`run_tasks_worker` after code changes.
- No linter, formatter or typechecker is configured. Don't add tooling or mass-reformat; match surrounding style.

## Architecture

| App | Owns |
|---|---|
| `app_factory` | Reference data: factories → workshops → lines, products → packagings (GTIN) → SKUs, production locations; `UserFactory` (user→factory), `selectors.py` |
| `app_uip` | Core entities: `UIP`, `ProductionParty`, `UIPStatusLog`; services `uip_reserve`, `reserve_accumulation`, `party_sync` |
| `app_cz` | Chestny Znak: `CISCode`/`CISCodeArchive`, `SUZAccount`, services (`suz_client`, `true_api_client`, `party_service`, `code_client`, `code_sync`, `code_status`, `code_archive`, `desync_resolution`, `order_service`, `nk_sync_state`, `national_catalog_client`, `reserve_monitor`, `rate_limit`) |
| `app_scheduler` | `SCHEDULE`, task registry/progress, `tasks.py`, `run_scheduler`/`run_tasks_worker` |
| `app_page` | Page views only: main, search, `/uip/`, product control `/products/`, SUZ orders `/suz/` |
| `app_helper` | `UUIDModel`, middleware, `access.py`, `search_helper.py`, `sign_helper.py`, `load_tracker.py`, `metrics.py`, `external.py` |
| `app_event` | `EventLog` + `log_event()` (`utils.py`), `HealthCheck`, `NotificationRecipient`, `services/health.py` |
| `app_wms` | Empty skeleton |
| `config` | Settings package **and** a Django app (`ExternalService`) |

- `config/urls.py` mounts `app_page` at `/` (main/search/`/uip/`/`/products/`/`/suz/`), plus `/cz/`, `/uip/`, `/factory/`, `/wms/`, `/scheduler/`, `/monitoring/`, `/helper/`, `/health/`, `/auth/`, Swagger at `/api/docs/`.
- **CZ admin/API views live in `app_cz/views.py`** (NK sync/progress/product, UIP generate/sync, Molvest task sync), not `app_page`. `app_page/views.py` holds page views, including product control and SUZ. `app_uip/urls.py` is DRF-only: `api/v1/search`, `reserve-uips`, `product-by-gtin`, `status_parties`.
- Service-layer pattern: `app_cz`, `app_factory`, `app_uip`, `app_event` use `services/`. `app_helper/external.py::safe_external_call(func, ...)` wraps non-critical external calls, logs an `EventLog` and returns `(result, error)` instead of raising.

## Critical conventions

- Models extend `UUIDModel` (`app_helper/models.py`, time-ordered UUIDv7 via `UUID7Field`). Don't use plain `models.Model`/`UUIDField` for business entities. Exception: log/observability tables (`app_event.EventLog`/`HealthCheck`/`NotificationRecipient`, `app_scheduler.TaskProgress`) deliberately use `models.Model`.
- **`config/.env` is the only config source** (python-dotenv in `config/settings.py`). It is gitignored and there is no `.env.example`; a fresh checkout must create it (DB credentials, `SECRET_KEY`, `DEBUG`, `TIME_ZONE`/`IS_TIME_ZONE`, optional notification/`HEALTH_*` vars). `help.txt` and README document the variables. `SESSION_COOKIE_NAME` defaults to the stable `pms_sessionid` — a random default used to log everyone out on restart. `USE_TZ` is on only when `IS_TIME_ZONE=1`, so times are naive by default — be explicit with aware datetimes.
- **Migrations are gitignored** (`**/migrations/*.py`), so they never appear in `git status` and aren't shared. After a model change run `makemigrations` + `migrate` on **both** DBs on each machine. Only `config/migrations/0001_initial.py` is tracked. Tables for progress/metrics/NK lock soft-fail when missing, so a stale DB degrades silently rather than erroring.
- **Two databases** (`default`, `archive`). `app_cz.CISCodeArchive` is routed to `archive` by `app_cz/routers.py` (denormalized snapshot, no FKs); query with `.using('archive')`. `DB_ARCHIVE_*` env vars fall back to the `default` values.
- **Access uses Django Groups, not `is_superuser`.** `app_helper/access.py`: `is_admin` (superuser OR `is_staff` OR group «Админ»), `can_view_uip` (admin OR «Просмотр» OR `app_uip.view_uip`), `can_generate_uip` (admin OR `app_uip.add_uip`/`change_uip`). Groups «Админ», «Просмотр», «Мониторинг» are created by a `post_migrate` receiver (`app_helper/signals.py`). Use `AdminRequiredMixin`/`admin_required`/`admin_required_json`/`generate_uip_required_json` and the `is_admin`/`can_view_uip`/`can_generate_uip` context flags (`config.context_processors.user_context`) instead of `user.is_superuser`.
- **Per-factory access.** `get_user_factory(user)` (backed by `UserFactory`) scopes a **non-admin** user to one factory; **admins (superuser/`is_staff`/«Админ») and unbound users get `None` → they see everything.** Helpers `filter_uips_for_user`, `user_can_access_uip`, `user_can_access_sku`: a UIP is "own" if its SKU has a `ProductProductionLocation` at the factory or it has a `ProductionParty` there. Applied in `UIPListView`, `GenerateUIPView` (403 for foreign SKU), the product card and per-UIP DRF actions.
- **`/products/`** (product control) allows inline POST edits (`target=product|sku|packaging|location`) scoped to the product; foreign ids → 404. Any logged-in user may open it.
- **`get_available_products()`** feeds the `/uip/` generation dropdown (≈400 SKUs): it prefetches `product__packagings` and `product_production_locations` (3 queries total) and returns the full product card (group/shelf life/type/packagings/factories) for the hover tooltip. Don't loop over products with `product.consumer_gtin` / `product_production_locations` — that reintroduces N+1 on every `/uip/` render.
- Status changes go through `UIP.change_status()`; every transition is audited in `UIPStatusLog` with source (`admin`/`sync`/`api`/`service`).
- **SUZ management is superuser-only.** The panel buttons («Настроить СУЗ», «Обновить», «Сбросить», modal) are shown only when `status_suz.can_manage` (`request.user.is_superuser`), and the endpoints `GET /cz/api/get-suz-certificates/`, `POST /cz/api/setup-suz-account/`, `POST /cz/api/reset-suz-account/`, `GET /cz/api/get-auth-key/`, `POST /cz/api/refresh-suz-token/` are guarded by `app_helper.access.IsSuperUser` (DRF permission). Don't relax them back to `IsAppAdmin` — these are sensitive account operations.

## Scheduled tasks

- **`SCHEDULE` in `app_scheduler/management/commands/run_scheduler.py` is the source of truth** for intervals (README's table can lag).
- Name→function mapping is centralized in `app_scheduler/registry.py::get_scheduled_tasks()`, shared by the scheduler, `/scheduler/status/` and `/scheduler/run/<name>/`. A new task needs entries in **both** `SCHEDULE` and the registry (`SchedulerRegistryTests` asserts they match).
- `FIXED_DAILY_TIMES` (same module) makes a task ignore its interval and run once a day at a fixed **local** time (`is_fixed_daily_due`/`next_fixed_daily_run`; currently only `accumulate_short_shelf_life_reserve` at 00:30). Scheduler and status API both honor it.
- A FAILED `sync_external_parties_codes` retries after `FAST_RETRY_INTERVAL` (5 min) instead of the full hour.
- **Task progress:** `app_scheduler/progress.py` writes `app_scheduler.TaskProgress` (one row per task, best-effort) via `set_task_progress`/`get_task_progress`/`clear_task_progress`. Tasks opt in with a `progress_name`; `/scheduler/status/` adds `is_running`/`is_queued`/`started_at`/`progress`, and the admin «Фоновые задачи» modal polls every 5 s.
- **Manual run:** `POST /scheduler/run/<name>/` (`SchedulerRunView`, `admin_required_json`) enqueues the task for the worker and returns 409 if a READY/RUNNING run exists. `<name>` is the `SCHEDULE` key.
- Tasks are django-tasks-db functions in `app_scheduler/tasks.py`; emails use `send_email_task` (queue `emails`), the rest use `default`. `high-priority` is configured but currently unused.

## Tests

- Real suites: `app_uip/tests.py` (largest: reservation, accumulation, search, roles), `app_cz/tests.py` (external sync/watermark, code sync, CZ status mapping, generation/reserve, admin paginator, SUZ), `app_factory/tests.py` (activity/`sku_links`, NK shelf life, packagings), `app_event/tests.py` (health/alerts, monitoring API), `app_scheduler/tests.py` (schedule, fixed daily, status, progress, manual run), `app_page/tests.py` (product control, factory scoping, SUZ page, status panel), `app_helper/tests.py` (load stats, request metrics, session cookie, ASGI logging). `app_wms/tests.py` is an empty stub.
- Tests need a reachable PostgreSQL (Django creates/drops a temp DB) and mock CZ/HTTP with `unittest.mock.patch` — no network or SUZ account needed.
- Page-render tests need the `STATIC_OVERRIDE` trick (`ManifestStaticFilesStorage` has no manifest in tests) and patch `config.context_processors.check_factories` / `app_helper.service_helper.diagnose_service` so the status widget doesn't hit the network.
- **CI does not run tests** — it only does `check`, migrations and `collectstatic`. Always run the relevant local suite.
- **Everything ships with tests.** Bug fixes add a test that reproduces the bug; new behavior covers happy/error/edge paths; behavior changes update existing tests.

## Search & big tables

- Unified search is `app_uip/views.py::api_search`, `GET /uip/api/v1/search/`, mirroring `/search/` via `app_helper.search_helper.detect_search_type` + `clean_datamatrix_code`; accepts `q`/`type`/`page`/`page_size` (default 25, max 100), returns `{query, search_type, count, page, page_size, in_archive, results}`.
- **Always exact match first.** `filter_codes_by_query`/`filter_uips_by_query` try `code__exact`/`number__exact` (unique index) before `code__istartswith`/`number__iexact`. A plain `Q(code__iexact) | Q(code__istartswith)` is a full scan of a multi-million-row table (`UPPER(code) LIKE …`) — don't revert. The prefix fallback depends on the functional index `cis_code_upper_prefix_idx` (`OpClass(Upper('code'), varchar_pattern_ops)`; needs `django.contrib.postgres`).
- **Codes are stored with the GS separator `\x1d`** (before AI 93), e.g. `...215umU':\x1d93E59s`. `filter_codes_by_query` checks both the raw query and its `clean_datamatrix_code`-stripped form; never clean the query before exact matching or scanner searches break.
- **Archive fallback:** codes older than 45 days move nightly to `CISCodeArchive` (`app_cz/services/code_archive.py`). `api_search` and `SearchView` query the working table first, then — for `code` searches only — `CISCodeArchive.objects.using('archive')`; the API sets `in_archive: true` (page shows «Код найден в архиве»). UIPs are never searched in the archive.
- `search` and `status_parties` are public (`AllowAny` is the DRF default); only `reserve-uips` requires admin (`IsAppAdmin`). `ProductSKU` has no `name` — serializers must use `product_sku.product.name` (the old `product_sku.name` broke `/status_parties/active/`).
- **`CISCode`/`CISCodeArchive` admin must stay fast on huge tables.** `CISCodeAdmin` orders by `-id`; there is **no index on `CISCode.created_at`**, so `-created_at` sorts millions of rows per page. Both admins use `LargeTablePaginator` (approximate count from `pg_class.reltuples` for the queryset's table **and DB alias**) with `show_full_result_count=False` — without it every changelist open runs a full `COUNT(*)`. `list_filter` on choice fields is cheap (`ChoicesFieldListFilter`).

## UIP numbers & generation

- **Format:** 14 GTIN digits + 6 date digits + 1–12 serial chars (regex-validated in the model).
- **Local numbers** (`app_cz/services/party_service.py::build_local_party_number`) branch on `ProductSKU.type_formation_uip`:
  - `general` = GTIN+date+`article[:5]` padded to 32;
  - `party_beginning` appends `party`; `party_end` pads the base to 29 then right-justifies a 3-digit `party`;
  - `natura` («НатураПРО») = GTIN(14)+date(6)+`0000-`+**exactly 7-digit** party (a line-marker suffix like `2635798g` is stripped). A non-7-digit Natura party returns `''` → `generate-uip` must 400.
  - Article is silently truncated to 5 chars for non-`natura` types.
- **The format is duplicated in JS — change both sides together.** `static/js/uip.js::buildLocalNumber`/`buildPreviewHint` mirror the server, and `updatePartyVisibility`/`validatePartyInput`/`submitGenerate` mirror the party rules (Natura = exactly 7 digits, others ≤ 3). The `/uip/` live preview is what users read, so a server-only change shows/submits a wrong number. Display splitting is `party_service.split_local_party_number` via `app_page/templatetags/uip_display.py` tags. Local convention: `GTIN(14) + дата ГГММДД(6) + партия(12)`.
- **CZ generation (`mode='cz'`)** goes `generate_uip` → `_generate_cz_uip(product_sku, gtin, production_date)` (pass the **SKU object**) → `generate_party_numbers`. TrueAPI `party-numbers/generate` requires `productionDate` as a full ISO datetime `%Y-%m-%dT%H:%M:%S.000Z` (date-only is rejected), `partyNumberInfo` items `{gtin, productionDate, count}`, and `pg` = `Product.group`.
- **Burned UIP re-reservation:** a request for an existing `deleted` UIP re-reserves the same number in CZ (`reserve_parties_honest_sign`) and `_restore_burned_uip`/`restore_burned_uips` refresh `reservation_date`, clear `is_desync` and set `reserved_local`. `skip_cz=True` and non-deleted existing UIPs keep the old "уже существует" behavior.

## CZ / SUZ / Molvest integration

**External task code sync (`app_cz/services/code_sync.py`).**
- The Molvest server returns `sntins_camera` (applied) + `sntins_printer` (pending) and moves codes printer→camera as they are applied. After `sync_codes_task`, `produced_quantity` («Факт») is recalculated as the count of APPLIED codes (`_update_party_produced_quantity`), not from `amount`, or «План/Факт» goes stale.
- `status=DELETED` tasks are marked `SYNCED` (both in `receive_external_task` and `sync_all_external_tasks`) so they don't hang in «Ожидают синхронизации».
- `sync_all_external_tasks` pulls codes only for parties in `CODE_SYNC_STATUSES` (`work`/`closed`) with `external_created_at` within `CODE_SYNC_WINDOW_DAYS` (3); older/other-status tasks are skipped (stage-1 intake still stores all statuses). Leftover ineligible `PENDING` parties are bulk-marked `SYNCED` — don't leave them `PENDING`; a task re-pushed externally returns to `PENDING` via `receive_external_task`.
- **Two code-response formats:** `/codes/api/get_codes_by_task/` may include structured `codes: [{'code','level','parent_code'}]` alongside the flat lists. `sync_codes_task` prefers `codes` when non-empty and derives APPLIED/PENDING by matching against the flat lists — keep that merge (the structured format carries no status).
- **Per-factory task-pull watermark:** `sync_external_parties_and_codes` pulls tasks changed since `Factory.external_sync_changed_since`; each factory's watermark advances only on its own successful fetch (`WATERMARK_SAFETY_MARGIN = 5 min`). `_fetch_external_tasks_changed_since` returns `None` (not `[]`) on network/response errors so a failed factory retries the window next run; failures surface in `failed_factories` and the scheduled task raises so `DBTaskResult` becomes FAILED. Manual full pull: `POST /cz/sync/all/` (`SyncAllTasksView`).
- **Tasks without uuid are skipped:** `receive_external_task` accepts a task only if it has `uuid_str`/`uuid_task` («Задание (Внешнее)» must be a uuid). Old/test tasks with numeric ids return `{'has_error': True, 'skipped_no_uuid': True}` and are not counted as sync errors.

**Desync (`app_cz/services/desync_resolution.py`, hourly `resolve_desync_uips`).** For each `is_desync=True` UIP (except `draft`/`deleted`), codes from its external tasks are checked against CZ via batched `/cises/info` (per product group); if there are no local codes, one is fetched from the factory server (`get_any_code_for_task`). `APPLIED`/`INTRODUCED` means the marking report was formed: `reserved_*` → `registered` (then the usual `closed`/`archived` ladder), `registered`/`closed`/`archived` just lose the flag. UIPs with no codes at all fall back to the CZ reserve list: present → reserved, absent → registered, list unavailable → stay. `sync_parties` does **not** flag `draft`/`deleted` and clears stale flags (`_clear_draft_deleted_desync`); it re-flags a registered UIP that CZ still lists as reserved, and samples only ONE code per UIP (`_collect_uip_codes`) while the resolver checks up to `MAX_CODES_PER_UIP`.

**Desync UI (`/uip/?desync=1`).** An admin sees «Проверить в ЧЗ» → `POST /cz/api/check-uip-cz/` (`api_check_uip_cz` → `reserve_party_numbers_cz`, bypassing the local duplicate check). Success (number was free) → `reserved_local`, flag cleared. CZ refusal → check codes: APPLIED/INTRODUCED → `registered`; otherwise the CZ reserved-parties list decides (present → `reserved_local`/`reserved_cz` with drafts included, absent → `registered`); list unavailable → stays in desync. Always HTTP 200 with `result` = `reserved`/`registered`/`desync`.

**True API rate limits** are enforced by `app_cz/services/rate_limit.py` (`wait_nk_endpoint` in `NationalCatalogClient._make_request`): `/nk/product` max 10 req/5 min, other NK methods 10 req/s. The limiter paces evenly (min interval = window/limit); don't revert to burst-then-stall — it froze sync progress.

**NK → Product sync (`app_factory/services/nk_sync_service.py`).**
- Supplier codes (`article`/`other_codes`) live in the `good_attrs` attribute `Код товара в учетной системе поставщика` (not `attrs`), comma-separated.
- `ProductSKU` has no `created_at`; use `.order_by('id')` for "first created".
- A product can have multiple packagings of the same level; `ProductPackaging` has no unique constraint on `(product, level)` — uniqueness is by `gtin`, and sync keys `update_or_create` on `(product, gtin)`. `_parse_nc_packagings` maps `identified_by`: `trade-unit`→UNIT, `inner-pack`/`box`→GROUP, `layer`/`pallet`→TRANSPORT, with `multiplier` as `quantity_inside`.
- UIP sync looks up SKU by consumer GTIN via `find_sku_by_gtin`; no SKU → skipped («не найден SKU»). **One product can have several articles per GTIN** (plate changes). `find_sku_by_gtin`/`find_any_sku_by_gtin` prefer the SKU with an active `sku_links` entry (`selectors.prefer_linked_skus`) — otherwise the alphabetically first stale article wins and `/cz/sync` shows an article Molvest doesn't use. `receive_external_task` relinks existing UIPs to `find_sku_for_factory(product, factory, article_prefix)`; when several SKUs are linked to the same factory, the prefix is taken from the **UIP number** (local format: GTIN+date+article[:5]), not from the task (a task may have no article), with the task's `product`/`article` only as a fallback for a new/`natura` number. `python manage.py relink_uip_skus [--article N] [--number N] [--dry-run] [--limit N]` relinks stored UIPs the same way.
- **`/nk/product` batch failures are isolated:** the API returns 400 for the whole 25-ID batch if one `good_id` is bad (deleted/foreign/kit). `fetch_products_resilient()` splits failing batches recursively (`MAX_SPLIT_DEPTH=5`) so only bad IDs drop; don't revert to `get_products()` in a bare try/except.

**NK sync is cross-process serialized** (`app_cz/services/nk_sync_state.py`): DB-backed singleton lock + progress (`NKSyncState`, row id=1, `SELECT ... FOR UPDATE`). Web and scheduled sync both call `try_start_sync()`; a concurrent attempt gets 409/skip (parallel syncs blew the API limit). Progress is written via the `SyncProgress(dict)` proxy so the NK page and «Фоновые задачи» both see it. Heartbeat stale timeout `LOCK_STALE_TIMEOUT = 10 min` with auto-takeover; `python manage.py reset_nk_sync` force-clears. If the table is missing, the service falls back to per-process memory instead of 500ing (no cross-process serialization until migrated).

**СУЗ token refresh (`app_cz/services/suz_client.py`).** `refresh_suz_dynamic_token()` retries the `/auth/key` → sign → `simpleSignIn/{connection_identifier}` chain up to `SUZ_TOKEN_REFRESH_ATTEMPTS` (3). `ensure_suz_token_valid()` refreshes proactively when expiry is within `SUZ_TOKEN_REFRESH_THRESHOLD` (1 h). The 6-hourly `refresh_suz_token` task delegates to it, and `health._diagnose` also calls it every 5 min before `check_suz_token` — keep the proactive refresh; the old 6 h interval vs 8 h lifetime caused «Динамический токен СУЗ истёк» alerts.

**SUZ orders (`/suz/`, admin-only).**
- `SuzOrdersView` (`app_page/views.py`) → `order_service.get_suz_orders` (`POST /api/v3/orders/search` with the active `SUZAccount.dynamic_token`). Default filter = active statuses only (`CREATED/PENDING/APPROVED/READY`; `status=all` = no filter), page size 10. `serviceProviderId` is resolved to `providerName / taxIdentificationNumber` (`get_suz_providers`, cached 1 h, raw ID fallback).
- `POST /suz/close/` (`SuzOrderCloseView`) closes one/many orders (`getlist` → `close_suz_orders`, no batch API) via `POST /api/v3/order/close` signed with `unpinned_signed_data` (`X-Signature`); partial failures are reported via Django messages.
- `order.can_close` = no `serviceProviderId` and status not `CLOSED`/`DECLINED`; provider orders show a disabled ✕ and no bulk checkbox; checkboxes belong to the external `#bulkCloseForm` via the HTML `form` attribute (no nested forms).
- `contactPerson` exists only in the create-order request (`attributes`), not in search results — extract tolerantly and hide the column if absent.
- Hourly `check_suz_orders` emails when active orders exceed `SUZ_ACTIVE_ORDERS_LIMIT` (default 90) to `SUZ_ORDERS_NOTIFICATION_EMAILS` (falls back to `UIP_RESERVE_NOTIFICATION_EMAILS`), every hour while exceeded.

## Reserve monitoring & accumulation

- `app_cz/services/reserve_monitor.py` fill thresholds (`UIP_RESERVE_LIMIT` = 10000): `>60%` warn, `>75%` critical, `>95%` emergency release of obsolete reserved UIPs (**`RELEASE_BATCH_SIZE = 1000`**, planned registration stays `REGISTER_BATCH_SIZE = 100`). For products with shelf life **<= 40 days** the emergency release prefers a code from the factory's general reserve by GTIN (`_fetch_code_by_gtin`) instead of the task code (`prefer_general_reserve` in `register_uip`); if GTIN code is unavailable it falls back to task/local codes. Registration sends the marking report with marking date = `min(production_date, today)`; expiry falls back to the marking date when the party has no `expiration_datetime`; UIPs without a production date are skipped.
- **`registered` is confirmed only by an actual reserve release.** `register_uip`/`close_party_reservation` send the report, then check the CZ reserved-parties list (`get_reserved_party_numbers`, `_confirm_reserve_release`): the UIP becomes `registered` **only if its number left the reserve within `BURN_DAYS` (30) days** of reservation. Still reserved → stay `reserved_*`; left after 30 days → burned, not registered; list unavailable → not confirmed. This prevents «УИП стал Зарегистрирован, хотя не снялся с резерва» and the desync it caused.
- **Draft reserve failures (`reserve_drafts_from_date`).** `_reserve_numbers` returns `(reserved, errors, failed)`: if CZ rejects a whole batch it retries the numbers one-by-one so only genuinely bad numbers are failed. A CZ-rejected number is marked **`registered`** (reason in `UIPStatusLog`, numbers/reasons in the summary and an `EventLog` warning); validation/network/token failures keep the draft (`token`/`network` also make `reserve_required_drafts_task` raise → FAILED). The task returns the `failed` count/list instead of failing for CZ rejections. **`reserve_parties_honest_sign` validates the product group first** (`ProductGroupChoices` without `null`): missing/`null` group → `error_kind='validation'`, no CZ request; CZ `ReservationRequest["pg"]` JSON errors are also classified as validation, so such UIPs stay drafts. `python manage.py restore_pg_failed_drafts [--apply]` reverts REGISTERED UIPs whose status log note contains that pg failure.
- `app_uip/services/reserve_accumulation.py` (daily 00:30) keeps one UIP per date over `[today; today + ProductSKU.reserve_days]` for active `TypeFormationUIP.general` SKUs whose `Product.shelf_life_in_days <= UIP_SHORT_SHELF_LIFE_DAYS` (default 45, inclusive).
- Shelf life `41..UIP_SHORT_SHELF_LIFE_DAYS` is reserved in CZ with the locally-built number (`reserved_local`) **always**, across the whole accumulation window; `<= UIP_DRAFT_SHELF_LIFE_DAYS` (default 40) stays **draft** until the production date reaches `SHORT_SHELF_LIFE_RESERVE_FROM` (**01.03.2027**, `app_cz/enums.py`), then is reserved (per-UIP decision in `_should_reserve_entry`). Explicit `skip_cz=False` forces reservation regardless of date — this is the forced reservation from a «Молвест.Маркировка» task. `UIP_DRAFT_MODE` no longer affects accumulation; in `generate_uip`/`_generate_local_uip` it is overridden by `force_reserve` (41–45 always, ≤40 from 01.03.2027). Drafts are converted by `reserve_drafts_from_date()` (41–45 — any date, ≤40 — `production_date >= 01.03.2027`) via the daily `reserve_required_drafts` task / `python manage.py reserve_required_drafts [--dry-run] [--limit N] [--date YYYY-MM-DD]`. Reservation is skipped when reserve > 95%. There is no CZ API to remove a number from the reserve — rollback can only change the local status, so existing reservations are left as-is.
- The same `should_reserve_in_cz(sku, production_date)` predicate lives in `app_cz/services/party_service.py` (re-exported from `reserve_accumulation`) and is reused by `GenerateUIPView` (`/cz/uip/generate/`, `mode='local'`) and `generate_uip` (`force_reserve`): 41–45 days are reserved in CZ even with `UIP_DRAFT_MODE=1`; ≤40 days only from 01.03.2027.
- `reserve_parties_honest_sign` tolerates already-reserved numbers: CZ rejects the whole batch with «В списке партий содержатся дубликаты», so they're dropped (`already_reserved`), the rest retried, and the accumulation records the dropped numbers locally as `reserved_local`.
- UIP creation is idempotent (`UIP.objects.get_or_create(number=...)`) in `sync_parties_from_cz` and accumulation — `sync_parties` (30 min) and accumulation can target the same deterministic number concurrently (`IntegrityError` on `app_uip_uip_number_key`).

## Observability (`app_event`)

- `run_health_checks()` (every 5 min, toggles `HEALTH_CHECK_ENABLED`/`SYSTEM_ALERTS_ENABLED`) writes one `HealthCheck` row per check (db/suz/signatures/factories/load/summary). A failure is confirmed only after `HEALTH_CONFIRM_ATTEMPTS` (default 3 ≈ 15 min) consecutive failures — single blips send nothing; a confirmed outage alerts **once**, and recovery alerts only if it had been confirmed. Alerts go to active members of groups in `NotificationRecipient`; «Мониторинг» is auto-created. Emails are text + styled HTML (`_build_alert_content` via `send_email_task(html_message=...)`). Old rows are pruned by `HEALTH_RETENTION_DAYS`. Public `GET /health/` returns 200/503. Reserve/burn emails still use `UIP_RESERVE_NOTIFICATION_EMAILS`.
- **Load tracking is two-layer.** `LoadTrackingMiddleware` (1) keeps a per-minute ring buffer in the web process (`app_helper/load_tracker.py`) and (2) measures duration, DB time/queries (`connection.execute_wrapper`), status class and in-flight peak, flushing per-minute rows to **`app_event.RequestMetric`** every `REQUEST_METRICS_FLUSH_SECONDS` (30 s) via PostgreSQL `INSERT … ON CONFLICT DO UPDATE` with **additive** updates (multi-process/restart safe). Traffic is split `user`/`bot`/`monitoring`; `MONITORING_PREFIXES` (`/health/`, `/helper/health/`, `/helper/api/v1/status_service/`, `/scheduler/status/`, `/cz/nk/api/progress/`, `/monitoring/`, `/api/docs/`, `/api/schema/`) are excluded; static/media ignored.
- Read side: `/monitoring/` + `/monitoring/api/metrics/?range=1h|24h|7d` (admin-only), `get_window_stats()` (sums, p95 from the `h_*` histogram, error rate, peak/min), `get_load_stats()` for health/status (alerts on requests/hour, p95 or 5xx rate; `has_data=False` → «нет данных» rather than a false «0, в норме» — the worker sees no live counters; this was a real 539/539-zeros incident). Metrics pruned daily by `prune_request_metrics` after `REQUEST_METRICS_RETENTION_DAYS` (14). Missing table → metrics auto-disable and fall back to live counters; don't reintroduce cache-based counters (LocMem can't cross processes).
- **Outbound calls and infrastructure are metered too (stage 2).** Every `requests.get/post/request` in `app_cz`/`app_factory`/`app_uip`/`app_helper` goes through **`app_helper/external_http.py`** (`external_http.get(service, url, ...)`, service = `cz`/`nk`/`suz`/`sign`/`factory`/`1c`), which records service/method/outcome/duration/endpoint into **`app_event.ExternalCallMetric`**; outcome is the exact HTTP error code (`404`, `500`, …), `timeout` or `error`, endpoint is a path template with `{id}` for uuid/number segments (`endpoint_label`), so the health message can name the failing endpoint. `rate_limit.wait_nk_endpoint` adds a synthetic `cz_rate_limit` wait (with the NK endpoint). **Don't call `requests.*` directly in services** — it silently drops out of the metrics. Health probes (`check_url_status`) use service `probe` and are excluded from the «Внешние API» error check. On each flush `app_helper/system_metrics.py` samples Postgres (`pg_stat_activity`, `pg_stat_database` deltas, size, `max_connections`) and Linux `/proc` (CPU/RAM/load; empty on Windows) into **`app_event.SystemMetric`** (gauge=max per minute, counter=sum). `get_queue_stats()` reads `DBTaskResult` (ready/running/oldest-ready age/p95 duration/failures) for the dashboard. Health checks now also include «Внешние API» (`EXTERNAL_ERROR_RATE_THRESHOLD`, `EXTERNAL_MIN_CALLS`), «Очередь задач» (`QUEUE_MAX_READY`, `QUEUE_MAX_READY_AGE_SECONDS`, `QUEUE_MAX_FAILED_PER_HOUR`) and «Соединения БД» (`DB_CONNECTIONS_THRESHOLD`). Host sampling also records `web_rss_mb` from `/proc/self/status`.
- **Retention & log noise.** `app_event/services/retention.py` owns retention: `EventLog` 90 days (`EVENT_LOG_RETENTION_DAYS`), `HealthCheck` 14 (`HEALTH_RETENTION_DAYS`), `UIPStatusLog` 365 (`UIP_STATUS_LOG_RETENTION_DAYS`), `DBTaskResult` 30 (`TASK_RESULT_RETENTION_DAYS`), metrics 14 (`REQUEST_METRICS_RETENTION_DAYS`). Daily tasks: `cleanup_event_logs`, `cleanup_old_logs`, `cleanup_old_task_results`, `prune_request_metrics`; manual report/cleanup — `python manage.py cleanup_logs [--cleanup]`. To avoid floods: `safe_external_call` dedups identical `EventLog`/error entries for 5 min (`cache.add`, per process), `check_url_status` logs a failing URL at most once per 5 min, the **status panel reads the latest `HealthCheck` snapshot** (worker writes every 5 min) instead of live probes on every render (live fallback only while there is no history or the snapshot is older than 30 min), and `UVICORN_ACCESS_LOG=0` disables per-request access logging.

## Product activity sync (`app_factory/services/product_activity_sync.py`, daily)

Pulls each factory's `product-list`, writes per-factory records into `ProductSKU.sku_links` JSON (`molvest_uuid` = our `Product.id`, `gtin`, `article`, `factory`, `active`), creates missing SKUs by article, and treats Molvest as the source of truth for `is_active` — **except** it never deactivates a SKU/product with a live UIP (`reserved_cz`/`reserved_local`/`registered`); a product is active iff any SKU is active. It also pushes `ProductSKU.type_formation_uip` to Molvest (`POST {factory}/workshop/api/v1/product-set-uip-type/` via `molvest_reference_sync.push_product_uip_type`) when `product-list` returns a different value; servers without the field are skipped. `check_molvest_products` is a read-only reconciliation report. **Reverse case:** an external task requesting a UIP for an inactive product reactivates the SKU/product via `party_service.find_or_activate_sku_for_task` before reserving — the task wins, and the reserved UIP then protects them from the next sync.

## CI/CD & deployment

- **CI** (`.github/workflows/ci.yml`) runs on every push/PR with a PostgreSQL 15 service: iconv-converts the UTF-16 `requirements.txt`, strips `pywin32`/`git+`, installs deps, then `manage.py check`, non-blocking `makemigrations --check --dry-run`, `makemigrations`, `migrate` on **both** DBs and `collectstatic`. It does **not** run tests.
- **Deploy** (`.github/workflows/deploy.yml`) runs on push to `main` or manually on a self-hosted runner (labels `linux, party-management`), using repo variable `DEPLOY_PATH`; it invokes `deploy.sh <branch>`.
- `deploy.sh`/`deploy.ps1`: `git pull --ff-only` → `docker compose build` → wait for DB healthy → gate `check`/`makemigrations`/`collectstatic` (aborts on failure) → `migrate` both DBs → `docker compose up -d --build` → post-check. `--check-only`/`-CheckOnly` stops after the gate.
- Docker is available but not the primary dev flow: `docker-compose.yml` has only `web` + `db`; the container CMD runs `makemigrations` → `migrate` (both DBs) → `collectstatic` → `exec python run_all.py` (so web+scheduler+worker live in `web`). It does **not** run `reset_nk_sync`. The Dockerfile patches `DB_HOST` into `settings.py` with `sed` and strips `pywin32`/`git+` from the requirements — don't mirror those hacks locally.

## Changelog (`docs/CHANGELOG.md`)

- **Only on explicit request.** The changelog is not updated with every change: write an entry only when the user asks for it and names the period ("за 3 дня", "за неделю"). If no period is given, ask first.
- **User-facing only.** Source: `git log` for the requested period plus the actual behavior. Describe what users see; no refactors, migrations, tests or internal details. Exception: external methods used by terminals/ТСД or «Молвест.Маркировка» may be mentioned.
- **Format.** Header: `## 20–22 Октября 2026. Изменения в приложении «СУП»`, then `###` sections by area (e.g. «СУЗ», «УИП», «Генерация УИП», «Синхронизация заданий», «Мониторинг», «Исправления»). Write for the user, not the developer: no URLs, method or model names; name sections/pages exactly as they are labeled in the UI.
- **Item layout.** `###` section heading, then items as `- Тема.` on its own line; the explanation follows on the next line (1–3 sentences, no blank line between topic and explanation; a blank line between items). No bold labels; plain user language, without «Где:»/«Что изменилось». For new pages/buttons write «Новое» and how to find them.
- **Ordering.** New entries on top; never rewrite old entries (only entries of the same period may be merged).

## Other gotchas

- **Graceful shutdown; `CancelledError` in logs is normal.** `run_all.py` handles SIGTERM/SIGINT (terminates children, waits 15 s, then kills), uvicorn uses `--timeout-graceful-shutdown 10`, and `config/asgi.py` turns `asyncio.shield`'s «CancelledError exception in shielded future» into one INFO line. Many such lines mean restarts/reloads, not a slow endpoint.
- **Versioning is tag-driven** (setuptools-scm → `config/_version.py`, gitignored). Commit subjects use `Feat:`/`Fix:`/`Docs:`; README maps fix→patch, feat→minor. Release: `git tag -a v2.0.0 -m "..."`.
- **`helper_info/`** (untracked) holds authoritative Chestny Znak specs: `True_API_GIS_MT.txt` (TrueAPI + National Catalog methods/rate limits — source for `rate_limit.py`) and `API_СУЗ_3.0.txt`. Consult them before changing CZ behavior instead of guessing from the web.
- External marking-server URLs are per factory (`Factory.ip_address`/`port_address`), not `.env`.
- Live events: use `log_event()` (`app_event/utils.py`: module/level/message/actor/metadata) instead of ad-hoc logging.
- Management commands: `app_cz`: `archive_old_codes`, `reset_nk_sync`, `relink_uip_skus`; `app_factory`: `sync_molvest_reference`, `check_molvest_products`; `app_event`: `cleanup_logs` (отчёт по ретеншну, `--cleanup` — очистка); `app_scheduler`: `run_scheduler`, `run_tasks_worker`.
- **`requirements.txt` is UTF-16LE** (BOM `FF FE`), so read/edit tools see binary. Keep the encoding (iconv in Docker/CI) and note the self-referential `-e git+…` line that CI/Docker strip.
- **`docs/`** is tracked Russian documentation (`01-overview`…`10-presentation-outline`, `CHANGELOG`); it is derived and partly stale (e.g. CHANGELOG claims `docs/` is gitignored). Treat code, README and this file as the source of truth.

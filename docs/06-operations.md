# 06. Запуск, конфигурация и эксплуатация

## Требования

- Python 3.14+
- PostgreSQL
- Зависимости из `requirements.txt` (файл в UTF-16LE) и установка проекта `pip install -e .`
  (генерирует `config/_version.py` из git-тегов).

> Зависимости лежат в `.venv` (gitignored). Системный `python` может не иметь Django —
> активируйте venv (`.venv\Scripts\Activate.ps1`) или вызывайте `.venv\Scripts\python.exe`.

## Быстрый старт

```bash
# Всё сразу: web + scheduler + worker
python run_all.py

# По отдельности
uvicorn config.asgi:application --host 0.0.0.0 --port 8888
python manage.py run_scheduler
python manage.py run_tasks_worker

# Миграции
python manage.py makemigrations <app_label>
python manage.py migrate
python manage.py migrate --database archive
```

`run_all.py` привязывает uvicorn к LAN-IP машины и включает `--reload` только при `DEBUG=1`.

## Конфигурация (`config/.env`)

Единый источник настроек (читается `python-dotenv` в `config/settings.py`).

| Переменная | Описание |
| --- | --- |
| `DEBUG` | `1` — разработка, `0` — прод |
| `SECRET_KEY` | Секретный ключ |
| `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_HOST` | Рабочая БД |
| `DB_ARCHIVE_*` | Архивная БД (по умолчанию = рабочая) |
| `TIME_ZONE`, `IS_TIME_ZONE` | Часовой пояс / `USE_TZ` |
| `UIP_RESERVE_LIMIT` | Лимит зарезервированных УИП (по умолчанию 10000) |
| `UIP_RESERVE_NOTIFICATION_EMAILS` | Получатели уведомлений |
| `UIP_SHORT_SHELF_LIFE_DAYS` | Срок годности (дней), не выше которого (включительно) накапливается резерв УИП (по умолчанию 45) |
| `UIP_DRAFT_SHELF_LIFE_DAYS` | Срок годности (дней), не выше которого (включительно) при накоплении создаются черновики; выше — резерв в ЧЗ (по умолчанию 40) |
| `UIP_DRAFT_MODE` | `1` — черновики без ЧЗ (по умолчанию), `0` — резервировать в ЧЗ. На накопление резерва не влияет |
| `EMAIL_*`, `DEFAULT_FROM_EMAIL` | Настройки почты |

- Адреса серверов маркировки — **per-factory** в модели `Factory` (`ip_address`, `port_address`),
  не в `.env`.
- Не читайте переменные окружения вне `settings.py`.

## Периодические задачи

Расписание — список `SCHEDULE` в `app_scheduler/management/commands/run_scheduler.py`
(таблица в `README.md` может отставать). Основные:

- Обновление токена СУЗ — каждые 6 ч (до 3 попыток при неудаче); плюс **заранее
  за час до истечения** внутри проверки состояния.
- Проверка состояния системы (`check_system_health`) — каждые 5 минут. Сбой подтверждается
  после 3 неудачных проверок подряд (~15 мин), алерт один раз.
- Сверка резерва УИП с ЧЗ (`sync_parties`) — каждые 30 минут.
- Синхронизация заданий и кодов с «Молвест.Маркировка» — раз в час (коды — только по
  заданиям «В работе»/«Закрыто» за последние 3 дня).
- Удаление/закрытие/архивация УИП, очистка логов — раз в сутки.
- Синхронизация справочников и Нац. каталога — раз в сутки.
- Мониторинг резерва — раз в час; сгорание/регистрация УИП и архивация кодов — раз в сутки.
- Проверка активности продуктов на заводах — раз в сутки (перед накоплением резерва).
- Накопление резерва УИП на дни вперёд — раз в сутки.

## Мониторинг резерва УИП

| Заполнение | Действие |
| --- | --- |
| > 60% | Email-предупреждение |
| > 75% | Email-тревога |
| > 95% | Тревога + снятие устаревших УИП (не более 100 за запуск) |

Контроль сгорания: предупреждение, если до сгорания осталось < 7 дней.

**Сверка резерва с ЧЗ.** Задача `sync_parties_task` (`sync_parties_from_cz`,
каждые 30 минут) сверяет список зарезервированных партий ЧЗ с локальными
`reserved_cz`/`reserved_local`:

- новых УИП из ЧЗ создаёт; статус определяется по формату номера: если номер
  совпадает с локальным (`build_local_party_number` по типу формирования SKU)
  → `reserved_local` (зарезервирован вручную), иначе `reserved_cz`;
- локальные зарезервированные, которых в ЧЗ уже нет (партия ушла из резерва
  после отчёта о нанесении), проверяются по кодам: берётся по одному коду из
  заданий УИП и **одним пакетным запросом** (`POST /cises/info`, до 1000 кодов)
  запрашивается фактический статус в ЧЗ. Код `APPLIED`/`INTRODUCED` → УИП
  переводится в `registered`; иначе — `is_desync=True`.

Отдельные одиночные запросы к ЧЗ не делаются (риск блокировки за спам).

**Ручная проверка рассинхрона (`/uip/`).** На странице есть кнопка-фильтр «В рассинхроне»
(показывает `is_desync=True`). Для такой строки админ может нажать «Проверить в ЧЗ»
(`POST /cz/api/check-uip-cz/`) — система пробует зарезервировать номер напрямую в ЧЗ:

- успех → номер был свободен (резерв снят), УИП возвращается в `reserved_local`, `is_desync` снимается;
- отказ ЧЗ → номер уже зарегистрирован/занят, статус не меняется (результат «зарегистрирован»).

**Ручная регистрация УИП.** В таблице на `/uip/` в колонке «Взаимодействие»
для зарезервированных УИП с привязанным заданием есть кнопка **«Отправить
отчёт о нанесении»** (`POST /cz/api/report-uip/`, админ). Код берётся из
задания, дата маркировки — дата производства УИП, вместо срока годности —
срок годности задания, если он есть, иначе дата производства. Если задания
нет — кнопка не показывается.

### Проверка активности продуктов

Задача `sync_product_activity_task` (раз в сутки, до накопления резерва)
запрашивает у сервера каждого завода `GET {Factory.ip_address:port}/
workshop/api/v1/product-list/`. SKU, привязанные к линиям завода, но
отсутствующие в списке или помеченные `active=false`, деактивируются
(`ProductSKU.is_active=False`); если у продукта не остаётся активных SKU —
продукт тоже становится неактивным. При недоступности завода его SKU
не трогаются (сбой фиксируется в `failed_factories`).

### Накопление резерва УИП на дни вперёд

Задача `accumulate_short_shelf_life_reserve_task` (ежедневно в **00:30**, местное
время) доливает резерв
для активных SKU **обычного** формата (`ProductSKU.type_formation_uip =
«Обычный»`), у продукта которых срок годности не больше `UIP_SHORT_SHELF_LIFE_DAYS`
(по умолчанию 45 дней, включительно):

- окно дат — `[сегодня; сегодня + ProductSKU.reserve_days]` (поле «Резерв УИП,
  дней», по умолчанию 5 → 6 дат); доливается всё окно, пробелов не остаётся;
- на одну дату — ровно один УИП; если УИП уже есть, новый не создаётся;
  «сгоревший» (`deleted`) УИП повторно резервируется тем же номером;
- номер формируется локально (`build_local_party_number`);
- срок годности **41–`UIP_SHORT_SHELF_LIFE_DAYS`** — УИП резервируются в ЧЗ
  **собственным (локальным) номером** (`reserved_local`) пачками ≤ 50 с
  паузой 10 сек между запросами; генерация номеров самим ЧЗ не используется;
- срок годности **не более `UIP_DRAFT_SHELF_LIFE_DAYS`** (по умолчанию 40) —
  создаются **черновики без обращения к ЧЗ**; при явном `skip_cz=False` такие
  УИП тоже резервируются в ЧЗ;
- при резервировании в ЧЗ, если заполнение резерва > 95% — резервирование
  пропускается (чтобы не ухудшать). Для черновиков порог не применяется.

Жизненный цикл УИП (сгорание 30 дней, статусы, пороги 60/75/95%) не меняется.

### Режим черновиков (`UIP_DRAFT_MODE`)

`UIP_DRAFT_MODE` (`.env`, по умолчанию `1`) задаёт глобальное поведение
`skip_cz` при генерации УИП, когда параметр не передан явно:
- `1` — создавать **черновики** без обращения к ЧЗ (безопасно, для оценки объёмов);
- `0` — сразу **резервировать** номера в ЧЗ.

Явный `skip_cz` в запросе (API/веб) имеет приоритет над настройкой. Действует
для генерации УИП (`generate_uip`, `reserve_uips`, `/cz/api/v1/generate-uip/`).
На **накопление резерва** (`accumulate_short_shelf_life_reserve`) настройка не
влияет: там режим определяется сроком годности продукции (см. выше).

## Наблюдаемость (health-проверки и алерты)

Задача `check_system_health_task` (раз в 5 минут) прогоняет проверки: БД, СУЗ
(токен), **сервис подписей**, серверы заводов, 1С, нагрузка. Результаты пишутся
в `app_event.HealthCheck` (история; записи старше `HEALTH_RETENTION_DAYS=28`
удаляются). При **смене состояния** сервиса (ок→сбой или восстановление)
пишется событие в `EventLog` и отправляется письмо получателям группы
**«Мониторинг»**.

- Получатели задаются моделью `NotificationRecipient` (FK на Django-группу,
  вкл/выкл), управляются в админке. Email-адреса берутся из `User.email`
  активных пользователей выбранной группы. Чтобы рассылка работала: задайте
  email пользователям, добавьте их в группу («Мониторинг» создаётся
  автоматически после `migrate`) и заведите для неё `NotificationRecipient`.
- Публичный эндпоинт для мониторинга: `GET /health/` (200/503, JSON: `status`,
  `version`, `checks`). Дублируется под `/helper/health/`.
- Настройки: `HEALTH_CHECK_ENABLED`, `SYSTEM_ALERTS_ENABLED`,
  `HEALTH_RETENTION_DAYS`, `SIGNATURE_SERVICE_URL` (опционально — адрес сервиса
  подписей; иначе берётся из `ExternalService`).
- Текущее состояние сервисов доступно в виджете «Фоновые задачи»
  (`/scheduler/status/`, поле `system_health`).

## Миграции

- Миграции **gitignored** (`**/migrations/*.py`, кроме `config/migrations/0001_initial.py`) —
  после изменения моделей запускайте `makemigrations` + `migrate` на каждой БД/машине.
- CI генерирует миграции из моделей; деплой применяет их на обеих БД.

## Docker

`docker-compose.yml`: сервисы `web` + `db` (Postgres 15). Контейнер `web` выполняет
`makemigrations` + `migrate` (обе БД) → `collectstatic` → `run_all.py`.
Docker — не основной dev-поток.

## CI/CD

| Workflow | Файл | Что делает |
| --- | --- | --- |
| CI | `.github/workflows/ci.yml` | При push/PR: Postgres 15, установка зависимостей (iconv UTF-16 → UTF-8), `check`, `makemigrations`, `migrate` (обе БД), `collectstatic` |
| Deploy | `.github/workflows/deploy.yml` | При push в `main` или вручную: self-hosted runner (`linux, party-management`), вызов `deploy.sh` |

Ручной деплой: `./deploy.sh [branch] [--check-only]` (Linux) или
`.\deploy.ps1 -Branch main [-CheckOnly]` (Windows). Скрипт: `git pull --ff-only` → сборка →
ожидание БД → gate (`check`/`makemigrations`/`collectstatic`) → миграции обеих БД → `up -d --build`
→ пост-проверка.

- Swagger: `/api/docs/`, схема: `/api/schema/`.

# PartyManagementSystem

Система управления производственными партиями и кодами маркировки в интеграции с системой «Честный Знак» (СУЗ / TrueAPI).

Система автоматизирует полный жизненный цикл партии: справочники производства (заводы, цеха, линии, номенклатура), генерацию и резервирование УИП (уникальных идентификаторов партий), работу с кодами маркировки (DataMatrix), синхронизацию статусов с «Честным Знаком» и контроль их рассинхрона.

### Приложения подробнее

- **app_factory** — справочники: заводы, цеха, линии; продукты, упаковки (GTIN с уровнями: потребительская/групповая/транспортная), номенклатура (SKU, в т.ч. тип формирования УИП), привязка SKU к линиям производства.
- **app_uip** — ключевые сущности: `UIP` (уникальный идентификатор партии, формат: 14 цифр GTIN + 6 цифр даты + серийный номер), `ProductionParty` (задание на линии), `UIPStatusLog` (аудит всех переходов статусов). Все смены статуса — через единый метод `UIP.change_status()`.
- **app_cz** — интеграция с «Честным Знаком»: коды маркировки `CISCode` (иерархия parent/children, статусы со стороны ЧЗ и производства), учётные записи СУЗ (`SUZAccount`: сертификаты, ИНН, динамические токены), сервисы: `suz_client` (авторизация TrueAPI: auth key → session token → dynamic token), `party_service` (генерация/резервирование партий, генерация УИП 4 типов), `code_client`/`code_sync` (отчёты о нанесении, синхронизация кодов).
- **app_scheduler** — планировщик и воркер django-tasks + периодические задачи.
- **app_page** — страницы интерфейса на Django-шаблонах.
- **app_helper** — вспомогательный код: абстрактная модель с UUIDv7, middleware загрузки страниц, сервисы.
- **app_wms** — заготовка модуля склада.

### Жизненный цикл УИП

Статусы УИП: `draft` (черновик) → `reserved_cz` (сгенерирован) / `reserved_local` (зарезервирован) → `registered` (зарегистрирован) → `closed` (закрыта) → `archived` (в архиве); `deleted` (сгорел). Все переходы фиксируются в `UIPStatusLog` с указанием источника и инициатора.

## Тесты

Запуск всех тестов:

```bash
python manage.py test
```

Запуск тестов отдельного приложения (например, `app_uip` — там сейчас и живут тесты):

```bash
python manage.py test app_uip
```

Тесты используют стандартный раннер Django (`django.test.TestCase`). Для прогона создаётся временная тестовая база (в PostgreSQL) и автоматически уничтожается после завершения — никаких отдельных подготовительных шагов не требуется.

Важно:

- Внешние запросы к «Честному Знаку» (True API) в тестах мокаются через `unittest.mock.patch` — тесты не требуют сети и активной учётной записи СУЗ.
- Реальные тесты: `app_uip/tests.py`, `app_cz/tests.py` (устойчивость синхронизации: персональная метка завода, поведение при сбоях) и `app_scheduler/tests.py` (`_effective_interval`). В остальных приложениях (`app_factory`, `app_page`, `app_helper`, `app_wms`) файлы `tests.py` — пустые заглушки.
- Виртуальное окружение `.venv` активируется как обычно: на Windows — `.venv\Scripts\Activate.ps1`, иначе `source .venv/bin/activate` (или вызывать `.venv\Scripts\python.exe` напрямую).

## Периодические задачи

| Задача | Периодичность | Описание |
| --- | --- | --- |
| Обновление токена СУЗ | каждые 6 ч | Обновление динамического токена СУЗ (живёт 8 ч) |
| Проверка состояния системы | каждые 5 мин | БД, СУЗ, подписи, заводы, 1С; история в `HealthCheck`, алерты группам-получателям при смене состояния |
| Сверка резерва УИП с ЧЗ | каждые 30 мин | Сверка резерва ЧЗ с локальными; по кодам (пакетно `/cises/info`) ушедшие из резерва → `registered`, иначе `is_desync` |

| Закрытие УИП без использования | 1 раз в сутки | `registered` без производственных партий 15 дней → `closed` |
| Архивация закрытых УИП | 1 раз в сутки | `closed` без активности 30 дней → `archived` |
| Очистка старых логов | 1 раз в сутки | Удаление логов статусов старше 700 дней |
| Проверка активности продуктов | 1 раз в сутки | Сверка с `product-list` заводов; снятые с производства SKU деактивируются |
| Накопление резерва УИП | 1 раз в сутки | Долив резерва УИП на дни вперёд для короткоживущей продукции (< 40 дней, обычный формат) |

## Мониторинг резерва УИП

Система отслеживает заполнение резерва зарезервированных УИП относительно лимита, установленного «Честным Знаком» (по умолчанию **10000**), и уведомляет по почте:

| Заполнение | Действие |
| --- | --- |
| > 60% | Email-предупреждение |
| > 75% | Email-тревога |
| > 95% | Email-тревога + **снятие с резерва устаревших УИП** |

**Накопление резерва на дни вперёд.** Для активных SKU **обычного** формата (`type_formation_uip`), у продукта которых срок годности меньше `UIP_SHORT_SHELF_LIFE_DAYS` (по умолчанию 40 дней), система поддерживает резерв УИП на окно дат `[сегодня; сегодня + ProductSKU.reserve_days]` (поле «Резерв УИП, дней», по умолчанию 5 → 6 дней). На каждую дату создаётся один УИП; если УИП уже есть — он не дублируется, а «сгоревший» повторно резервируется тем же номером. Режим задаётся настройкой `UIP_DRAFT_MODE`: `1` (по умолчанию) — **черновики без обращения к ЧЗ** (оценка объёмов); `0` — номера резервируются в ЧЗ пачками ≤ 50 с паузой 10 сек, и при заполнении резерва > 95% накопление пропускается. Жизненный цикл УИП при этом не меняется.

**Снятие с резерва устаревших УИП** выполняется через отчёт о нанесении в ЧЗ для УИП, до «сгорания» которых осталось не более 5 дней (сгорание — 30 дней после резервирования), самые старые — первыми, не более 100 УИП за запуск:

- используются коды DataMatrix из заданий УИП, не находящиеся в статусе «нанесён» (по умолчанию это все коды);
- после успешного отчёта коды помечаются как нанесённые, УИП переводится в статус `registered`;
- если у УИП нет заданий — у внешнего сервиса «Молвест.Маркировка» запрашивается код по GTIN
  (`GET {url}/codes/api/get_code_by_gtin/?gtin=...`), и УИП привязывается к нему в отчёте о нанесении;
  адрес сервера завода определяется через место производства SKU (`ProductProductionLocation`).

**Настройки (`.env`):**

| Переменная | Описание |
| --- | --- |
| `UIP_RESERVE_LIMIT` | Лимит зарезервированных УИП (по умолчанию `10000`) |
| `UIP_RESERVE_NOTIFICATION_EMAILS` | Получатели уведомлений, через запятую |
| `UIP_SHORT_SHELF_LIFE_DAYS` | Срок годности (дней), ниже которого накапливается резерв УИП (по умолчанию `40`) |
| `UIP_DRAFT_MODE` | `1` — черновики без ЧЗ (по умолчанию), `0` — резервировать в ЧЗ; явный `skip_cz` в запросе важнее |
| `EMAIL_BACKEND` | Бэкенд почты (по умолчанию `console` — письма в консоль; для прода — SMTP) |
| `EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD`, `EMAIL_USE_TLS` | Настройки SMTP |
| `DEFAULT_FROM_EMAIL` | Отправитель писем |

## Синхронизация с внешним сервисом (Молвест.Маркировка)

Система обменивается данными заданий и кодов маркировки с внешним сервисом.

**Схема обмена:**

1. Внешний сервис запрашивает генерацию УИП через `POST /cz/api/v1/generate-uip/`. Ответ содержит:
   - `number` — номер УИП (партионный учёт);
   - `uuid_uip` — id УИП.
   Для связи с УИПом внешний сервис сохраняет `uuid_uip` в задании.
2. Внешний сервис периодически «пушит» данные задания в приёмник: `POST /cz/api/tasks/receive/` (поля модели Task: `uuid_str`, `uuid_uip`, `party`, `uip`, `status`, `start_work`, `end_work`, `date_work`, `date_marking`, `date_expiration`, `plan_amount`, `amount` и др.). Задание создаётся/обновляется как производственная партия, УИП привязывается по номеру (`uip`) или по id (`uuid_uip`).
3. Наш сервис периодически забирает коды маркировки из внешнего сервиса по заданию: `GET http://<ip>:<port>/codes/api/get_codes_by_task/?task_id=...`.

**Статусы задания:** активные — «Создано», «В работе», «Закрыто» (коды синхронизируются постоянно); финальный — «Завершено» (последняя синхронизация данных, далее задание не пересинхронизируется). Задание может иметь только один статус в момент времени.

**Адрес внешнего сервиса:** у каждого завода свой локальный сервер маркировки, поэтому адрес хранится в модели `Factory` — поля `ip_address` и `port_address`. Для партии сервер определяется через привязку линии → цех → завод (`ProductionParty.line.workshop.factory`).

**API:**

- `POST /cz/api/tasks/receive/` — приёмник задания из внешнего сервиса.
- `POST /cz/api/tasks/sync-codes/` — ручная синхронизация кодов задания (админ).
- `POST /cz/api/codes/sync-task/` — синхронизация кодов с явным указанием URL/задания (админ).
- `POST /cz/sync/all/` — полная ручная синхронизация (выгрузка изменённых заданий по всем заводам + коды), админ.

**Надёжность выгрузки заданий.** Метка `changed_since` хранится **персонально для каждого завода** (`Factory.external_sync_changed_since`) и сдвигается только при его успешной выгрузке. Сбой сети/завода не «съедает» окно изменений: при ошибке выгрузки метка не меняется, и окно будет повторено; сбой одного завода не влияет на остальные. При успехе метка сохраняется с зазором 5 минут (защита от гонок и расхождения часов). Если синхронизация завершилась с ошибкой, задача помечается FAILED, и планировщик повторяет её через 5 минут (а не через час).

**Страница «Синхронизация»** (`/cz/sync/`, вкладка в шапке для администраторов) — отслеживание заданий из внешнего сервиса: статус задания, статус синхронизации, дата последней синхронизации, сообщение/ошибка, кнопки ручной синхронизации.

## API поиска УИП и кодов маркировки

Единый метод поиска повторяет страницу `/search/`: тип запроса (номер УИП или код маркировки DataMatrix) определяется автоматически, а управляющие символы DataMatrix (GS/FNC1) при поиске кода отбрасываются.

| Метод | Назначение |
| --- | --- |
| `GET /uip/api/v1/search/?q=<запрос>` | Единый поиск по УИП или коду маркировки |
| `GET /uip/api/v1/status_parties/{number}/` | Статус одного УИП |
| `GET /uip/api/v1/status_parties/active/` | Список действующих УИП (фильтры: `search`, `gtin`, `product_article`, даты) |

Параметры поиска: `q` (обязательный), `type` (`code`/`uip` — принудительно задать тип), `page`, `page_size` (по умолчанию 25, максимум 100).

Если код не найден в рабочей таблице, поиск автоматически обращается к архиву (`CISCodeArchive`, коды старше 45 дней): в ответе `in_archive=true`, а у результатов `archived=true`. То же на странице `/search/` (пометка «Код найден в архиве»). УИП в архиве не ищутся.

Пример:

```bash
curl "http://<host>:<port>/uip/api/v1/search/?q=04601751026019260101500320000000"
```

```json
{
  "query": "04601751026019260101500320000000",
  "search_type": "uip",
  "count": 1,
  "page": 1,
  "page_size": 25,
  "results": [
    {
      "id": "0192f0...",
      "number": "04601751026019260101500320000000",
      "gtin": "04601751026019",
      "status": "reserved_local",
      "status_display": "Зарезервирован",
      "product_name": "Молоко 3,2%",
      "product_article": "50032",
      "planned_quantity": 1000,
      "produced_quantity": 0,
      "production_date": "2026-01-01",
      "reservation_date": "2026-01-01"
    }
  ]
}
```

Эндпоинты поиска и проверки статусов — публичные (без авторизации); резервирование УИП (`POST /uip/api/v1/reserve-uips/`) доступно только администраторам.

## Роли и доступ

Доступ разграничивается встроенными группами Django (создаются автоматически после `migrate`):

| Роль | Возможности |
| --- | --- |
| «Админ» | Полный доступ: список УИП, генерация и резервирование, синхронизация заданий, Национальный каталог, фоновые задачи, настройки СУЗ. |
| «Просмотр» | Только страница УИП. Генерация УИП доступна, если выдано право на запись в модель `uip` (`app_uip.add_uip` / `change_uip`). |

- Главная и страница поиска — публичные (без входа).
- Страница УИП (`/uip/`) требует входа и роль «Админ»/«Просмотр» (или право `app_uip.view_uip`).
- Суперпользователь и staff всегда считаются администраторами.
- Состав групп и права назначаются в админ-панели Django (`/admin/`).

Результаты поиска выводятся **карточками**: код/номер, продукт, GTIN, артикул, завод, цех, линия, внешний номер задания, внутренний номер партии, статусы и даты.

## Проверка работы сервисов и счётчик запросов

Панель статусов в шапке страницы проверяет внешние сервисы:

| Сервис | Как проверяется |
| --- | --- |
| СУЗ (Честный Знак) | Активная учётная запись и срок действия динамического токена |
| Молвест.Маркировка (Заводы) | HTTP-запрос к серверу каждого завода (`http://{ip}:{port}/`, ожидается ответ 2xx); адрес из модели `Factory` |
| 1С | HTTP-запрос к адресу из настройки `ONEC_URL` (`.env`) |

Результаты проверок кэшируются на 30 секунд, чтобы не «пинговать» внешние сервисы на каждом запросе.

В футере отображается **реальное количество запросов за последний час** (считает `LoadTrackingMiddleware` через кэш, см. `app_helper/load_tracker.py`) — вместо статического значения.

## CI/CD

### GitHub Actions

| Workflow | Файл | Назначение |
| --- | --- | --- |
| CI | `.github/workflows/ci.yml` | При push/PR поднимает PostgreSQL, ставит зависимости и прогоняет `manage.py check`, `makemigrations`, `migrate` (default + archive) и `collectstatic`. |
| Deploy | `.github/workflows/deploy.yml` | `git pull` ветки → `docker compose up --build` → проверки. Запускается вручную (`workflow_dispatch` с выбором ветки) или при push в `main`. |

**Требования для Deploy:** self-hosted runner, установленный на сервере деплоя, с метками
`linux` и `party-management`. Каталог проекта задаётся repository variable `DEPLOY_PATH`
(если не задана — используется workspace раннера). В каталоге должен лежать файл
`config/.env`. Ручной запуск: Actions → Deploy → Run workflow → выбрать ветку.

### Скрипт деплоя

Альтернатива Actions для ручного выката на сервере (Linux — `deploy.sh`, Windows — `deploy.ps1`):

```bash
./deploy.sh [branch] [--check-only] [--no-pull] [--no-build]
```

```powershell
.\deploy.ps1 -Branch main [-CheckOnly] [-NoPull] [-NoBuild]
```

Порядок действий скрипта:

1. `git fetch` / `checkout` / `pull --ff-only` указанной ветки (по умолчанию — текущей);
2. `docker compose build`;
3. запуск БД и ожидание готовности (`healthcheck`);
4. **gate-проверки** (останавливают деплой при ошибке): `manage.py check`,
   `manage.py makemigrations`, `manage.py collectstatic --noinput`;
5. применение миграций: `migrate` и `migrate --database archive`;
6. `docker compose up -d --build` и пост-проверка `manage.py check` в запущенном
   контейнере.

Флаг `--check-only` выполняет только шаги 1–4 (без миграций и запуска) — удобно
использовать как pre-deploy проверку.

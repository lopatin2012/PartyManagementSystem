# PartyManagementSystem

Система управления производственными партиями и кодами маркировки в интеграции с системой «Честный Знак» (СУЗ / TrueAPI).

Система автоматизирует полный жизненный цикл партии: справочники производства (заводы, цеха, линии, номенклатура), генерацию и резервирование УИП (уникальных идентификаторов партий), работу с кодами маркировки (DataMatrix), синхронизацию статусов с «Честным Знаком» и контроль их рассинхрона.

### Приложения подробнее

- **app_factory** — справочники: заводы, цеха, линии; продукты, упаковки (GTIN с уровнями: потребительская/групповая/транспортная), номенклатура (SKU, в т.ч. тип формирования УИП), привязка SKU к линиям производства.
- **app_uip** — ключевые сущности: `UIP` (уникальный идентификатор партии, формат: 14 цифр GTIN + 6 цифр даты + серийный номер), `ProductionParty` (задание на линии), `UIPStatusLog` (аудит всех переходов статусов). Все смены статуса — через единый метод `UIP.change_status()`.
- **app_cz** — интеграция с «Честным Знаком»: коды маркировки `CISCode` (иерархия parent/children, статусы со стороны ЧЗ и производства), учётные записи СУЗ (`SUZAccount`: сертификаты, ИНН, динамические токены), сервисы: `suz_client` (авторизация TrueAPI: auth key → session token → dynamic token), `party_service` (генерация/резервирование партий, генерация УИП 4 типов), `code_client`/`code_sync` (отчёты о нанесении, синхронизация кодов).
- **app_scheduler** — планировщик и воркер django-tasks + периодические задачи.
- **app_page** — страницы интерфейса на Django-шаблонах.
- **app_helper** — вспомогательный код: абстрактная модель с UUIDv7, middleware загрузки страниц, сервисы.
- **app_wms** — заготовка модуля склада.

### Жизненный цикл УИП

Статусы УИП: `draft` (черновик) → `reserved_cz` (сгенерирован) / `reserved_local` (зарезервирован) → `registered` (зарегистрирован) → `closed` (закрыта) → `archived` (в архиве); `deleted` (сгорел). Все переходы фиксируются в `UIPStatusLog` с указанием источника и инициатора.

## Тесты

Запуск всех тестов:

```bash
python manage.py test
```

Запуск тестов отдельного приложения, класса или метода:

```bash
python manage.py test app_uip

python manage.py test app_uip.tests.ReserveAccumulationTests.test_generate_count_loops
```

Тесты используют стандартный раннер Django (`django.test.TestCase`/`SimpleTestCase`). Для прогона создаётся временная тестовая база (в PostgreSQL) и автоматически уничтожается после завершения — отдельных подготовительных шагов не требуется, но нужен доступный PostgreSQL.

Важно:

- Внешние запросы к «Честному Знаку» (True API) и серверам заводов в тестах мокаются через `unittest.mock.patch` — тесты не требуют сети и активной учётной записи СУЗ.
- Реальные тесты: `app_uip/tests.py` (ядро УИП, сериализаторы, резервирование, накопление резерва, роли/доступ), `app_cz/tests.py` (устойчивость синхронизации, синхронизация кодов, генерация и резерв УИП), `app_factory/tests.py` (активность продуктов и `sku_links`, сроки годности НК, упаковки), `app_event/tests.py` (health-проверки и алерты), `app_scheduler/tests.py` (логика расписания: `effective_interval`, фиксированное время), `app_page/tests.py` (страница продукции, заводской доступ, рендер статус-панели) и `app_helper/tests.py` (сообщение нагрузки, имена проверок `diagnose_service`). `app_wms/tests.py` — пустая заглушка.
- Рендер-тесты страниц подменяют статику (`STORAGES`/`StaticFilesStorage`, см. `STATIC_OVERRIDE` в `app_page/tests.py`) и мокают `config.context_processors.check_factories` / `app_helper.service_helper.diagnose_service`.
- Виртуальное окружение `.venv` активируется как обычно: на Windows — `.venv\Scripts\Activate.ps1`, иначе `source .venv/bin/activate` (или вызывать `.venv\Scripts\python.exe` напрямую).

| Накопление резерва УИП | ежедневно в 00:30 | Долив резерва УИП на дни вперёд для короткоживущей продукции (≤ 45 дней, обычный формат) |

> Актуальное расписание — список `SCHEDULE` в `app_scheduler/management/commands/run_scheduler.py` (источник истины; таблица может отставать).

**Резервирование черновиков с 01.11.2026.** Если Честный Знак отклонил резерв отдельного номера, УИП считается **зарегистрированным** (причина сохраняется в истории статусов и в журнале событий), чтобы не оставлять его черновиком и не повторять резервирование. При ошибке токена СУЗ или сети УИП остаётся черновиком, а задача помечается FAILED. Если ЧЗ отклонил всю пачку, номера проверяются по одному: валидные резервируются, проблемные попадают в отчёт с количеством и причинами — по ним можно разобраться, не сформированы ли они неправильно.

## Мониторинг резерва УИП

Система отслеживает заполнение резерва зарезервированных УИП относительно лимита, установленного «Честным Знаком» (по умолчанию **10000**), и уведомляет по почте:

| Заполнение | Действие |
| --- | --- |
| > 60% | Email-предупреждение |
| > 75% | Email-тревога |
| > 95% | Email-тревога + **снятие с резерва устаревших УИП** |

**Накопление резерва на дни вперёд.** Для активных SKU **обычного** формата (`type_formation_uip`), у продукта которых срок годности не больше `UIP_SHORT_SHELF_LIFE_DAYS` (по умолчанию 45 дней, включительно), система поддерживает резерв УИП на окно дат `[сегодня; сегодня + ProductSKU.reserve_days]` (поле «Резерв УИП, дней», по умолчанию 5 → 6 дней). На каждую дату создаётся один УИП; если УИП уже есть — он не дублируется, а «сгоревший» повторно резервируется тем же номером. Продукция со сроком годности **от 41 до `UIP_SHORT_SHELF_LIFE_DAYS`** резервируется в ЧЗ **собственным (локальным) номером** (`reserved_local`) пачками ≤ 50 с паузой 10 сек; для срока годности **не более `UIP_DRAFT_SHELF_LIFE_DAYS`** (по умолчанию 40) создаются **черновики без обращения к ЧЗ**, кроме дат производства с **01.11.2026** (константа в коде) — они резервируются в ЧЗ. С 01.11.2026 действует общее правило: **любой УИП с такой датой производства резервируется в ЧЗ**, даже если запрошен черновик; существующие черновики переводит в резерв ежедневная задача `reserve_required_drafts`. При заполнении резерва > 95% резервирование в ЧЗ пропускается. `UIP_DRAFT_MODE` на накопление не влияет. Жизненный цикл УИП при этом не меняется.

**Снятие с резерва устаревших УИП** выполняется через отчёт о нанесении в ЧЗ для УИП, до «сгорания» которых осталось не более 5 дней (сгорание — 30 дней после резервирования), самые старые — первыми, не более **1000** УИП за запуск (аварийное освобождение резерва при заполнении > 95%):

- для продукции со сроком годности **40 дней и меньше** код для отчёта берётся из **общего резерва завода по GTIN** (а не из задания); если код по GTIN получить не удалось — используется код из задания/локальных кодов;
- для остальной продукции — коды DataMatrix из заданий УИП, не находящиеся в статусе «нанесён»;
- после успешного отчёта коды помечаются как нанесённые, УИП переводится в статус `registered`;
- если у УИП нет заданий — у внешнего сервиса «Молвест.Маркировка» запрашивается код по GTIN
  (`GET {url}/codes/api/get_code_by_gtin/?gtin=...`), и УИП привязывается к нему в отчёте о нанесении;
  адрес сервера завода определяется через место производства SKU (`ProductProductionLocation`).

## Синхронизация с внешним сервисом (Молвест.Маркировка)

Система обменивается данными заданий и кодов маркировки с внешним сервисом.

**Схема обмена:**

1. Внешний сервис запрашивает генерацию УИП через `POST /cz/api/v1/generate-uip/`. Ответ содержит:
   - `number` — номер УИП (партионный учёт);
   - `uuid_uip` — id УИП.
   Для связи с УИПом внешний сервис сохраняет `uuid_uip` в задании.
2. Внешний сервис периодически «пушит» данные задания в приёмник: `POST /cz/api/tasks/receive/` (поля модели Task: `uuid_str`, `uuid_uip`, `party`, `uip`, `status`, `start_work`, `end_work`, `date_work`, `date_marking`, `date_expiration`, `plan_amount`, `amount` и др.). Задание создаётся/обновляется как производственная партия, УИП привязывается по номеру (`uip`) или по id (`uuid_uip`).
3. Наш сервис периодически забирает коды маркировки из внешнего сервиса по заданию: `GET http://<ip>:<port>/codes/api/get_codes_by_task/?task_id=...`.

**Статусы задания:** «Создано», «В работе», «Закрыто», «Завершено» и др. Задание может иметь только один статус в момент времени.

**Синхронизация кодов (этап 2).** Коды маркировки забираются **только** по заданиям в статусе **«В работе»** и **«Закрыто»**, созданным **не раньше 3 дней назад** (по дате «Создано» задания, `ProductionParty.external_created_at`). Задания «Создано»/«Завершено» и более старые коды не тянут — это ограничивает объём. На этапе приёма заданий сохраняются все статусы. Задания, по которым коды не тянутся (статус вне фильтра или старше окна), помечаются «Синхронизировано», чтобы не копились в «Ожидают синхронизации»; при новом изменении внешний сервис вернёт задание в «Ожидает».

**Адрес внешнего сервиса:** у каждого завода свой локальный сервер маркировки, поэтому адрес хранится в модели `Factory` — поля `ip_address` и `port_address`. Для партии сервер определяется через привязку линии → цех → завод (`ProductionParty.line.workshop.factory`).

**API:**

- `POST /cz/api/tasks/receive/` — приёмник задания из внешнего сервиса.
- `POST /cz/api/tasks/sync-codes/` — ручная синхронизация кодов задания (админ).
- `POST /cz/api/codes/sync-task/` — синхронизация кодов с явным указанием URL/задания (админ).
- `POST /cz/sync/all/` — полная ручная синхронизация (выгрузка изменённых заданий по всем заводам + коды), админ.

**Надёжность выгрузки заданий.** Метка `changed_since` хранится **персонально для каждого завода** (`Factory.external_sync_changed_since`) и сдвигается только при его успешной выгрузке. Сбой сети/завода не «съедает» окно изменений: при ошибке выгрузки метка не меняется, и окно будет повторено; сбой одного завода не влияет на остальные. При успехе метка сохраняется с зазором 5 минут (защита от гонок и расхождения часов). Если синхронизация завершилась с ошибкой, задача помечается FAILED, и планировщик повторяет её через 5 минут (а не через час).

**Страница «Синхронизация»** (`/cz/sync/`, вкладка в шапке для администраторов) — отслеживание заданий из внешнего сервиса: статус задания, статус синхронизации, дата последней синхронизации, сообщение/ошибка, кнопки ручной синхронизации.

## API поиска УИП и кодов маркировки

Единый метод поиска повторяет страницу `/search/`: тип запроса (номер УИП или код маркировки DataMatrix) определяется автоматически, а управляющие символы DataMatrix (GS/FNC1) при поиске кода отбрасываются.

| Метод | Назначение |
| --- | --- |
| `GET /uip/api/v1/search/?q=<запрос>` | Единый поиск по УИП или коду маркировки |
| `GET /uip/api/v1/status_parties/{number}/` | Статус одного УИП |
| `GET /uip/api/v1/status_parties/active/` | Список действующих УИП (фильтры: `search`, `gtin`, `product_article`, даты; пагинация `page`/`page_size`) |

Параметры поиска: `q` (обязательный), `type` (`code`/`uip` — принудительно задать тип), `page`, `page_size` (по умолчанию 25, максимум 100).

Если код не найден в рабочей таблице, поиск автоматически обращается к архиву (`CISCodeArchive`, коды старше 45 дней): в ответе `in_archive=true`, а у результатов `archived=true`. То же на странице `/search/` (пометка «Код найден в архиве»). УИП в архиве не ищутся.

Пример:

```bash
curl "http://<host>:<port>/uip/api/v1/search/?q=04601751026019260101500320000000"
```

```json
{
  "query": "04601751026019260101500320000000",
  "search_type": "uip",
  "count": 1,
  "page": 1,
  "page_size": 25,
  "results": [
    {
      "id": "0192f0...",
      "number": "04601751026019260101500320000000",
      "gtin": "04601751026019",
      "status": "reserved_local",
      "status_display": "Зарезервирован",
      "product_name": "Молоко 3,2%",
      "product_article": "50032",
      "planned_quantity": 1000,
      "produced_quantity": 0,
      "production_date": "2026-01-01",
      "reservation_date": "2026-01-01"
    }
  ]
}
```

Эндпоинты поиска и проверки статусов — публичные (без авторизации); резервирование УИП (`POST /uip/api/v1/reserve-uips/`) доступно только администраторам.

## Роли и доступ

Доступ разграничивается встроенными группами Django (создаются автоматически после `migrate`):

| Роль | Возможности |
| --- | --- |
| «Админ» | Полный доступ: список УИП, генерация и резервирование, синхронизация заданий, Национальный каталог, фоновые задачи. **Управление СУЗ** (настройка, сброс, обновление токена, сертификаты) — только суперпользователь. |
| «Просмотр» | Только страница УИП. Генерация УИП доступна, если выдано право на запись в модель `uip` (`app_uip.add_uip` / `change_uip`). |

- Главная и страница поиска — публичные (без входа).
- Страница УИП (`/uip/`) требует входа и роль «Админ»/«Просмотр» (или право `app_uip.view_uip`).
- Суперпользователь и staff всегда считаются администраторами.
- Пользователь, привязанный к заводу (`UserFactory`, /admin/), видит и взаимодействует только со «своими» УИП и продукцией своего завода; администраторы и пользователи без привязки видят всё.
- Состав групп и права назначаются в админ-панели Django (`/admin/`).

Результаты поиска выводятся **карточками**: код/номер, продукт, GTIN, артикул, завод, цех, линия, внешний номер задания, внутренний номер партии, статусы и даты.

**Рассинхрон на `/uip/` (админ).** В тулбаре — кнопка «В рассинхроне» (`?desync=1`), показывающая только УИП с `is_desync=True`. Для такой строки доступна иконка **«Проверить в ЧЗ»** (`POST /cz/api/check-uip-cz/`): система пробует **зарезервировать номер в ЧЗ напрямую** (без локальной проверки дубликатов). Успех → номер был свободен (резерв снят), УИП возвращается в `reserved_local` и `is_desync` снимается. Отказ ЧЗ → статус кодов проверяется в ЧЗ (`/cises/info`): если код нанесён (`APPLIED`/`INTRODUCED`), УИП переводится в `registered` и `is_desync` снимается. Если код регистрацию не подтвердил — смотрим список резерва ЧЗ: номер в списке → статус приводится к `reserved_local`/`reserved_cz` (черновик тоже), `is_desync` снимается; номера нет и зарезервировать не удалось → уже зарегистрирован (`registered`). Список резерва недоступен → остаётся в рассинхроне (`desync`). Во всех исходах ответ 200 (`result`: `reserved` / `registered` / `desync`).

## Проверка работы сервисов и счётчик запросов

Панель статусов в шапке страницы проверяет внешние сервисы:

| Сервис | Как проверяется |
| --- | --- |
| СУЗ (Честный Знак) | Активная учётная запись и срок действия динамического токена; перед проверкой токен обновляется **заранее — за час до истечения** (до 3 попыток) |
| Молвест.Маркировка (Заводы) | HTTP-запрос к серверу каждого завода (`http://{ip}:{port}/`, ожидается ответ 2xx); адрес из модели `Factory`. На главной отображается компактно — сеткой чипов |
| 1С | HTTP-запрос к адресу из настройки `ONEC_URL` (`.env`) |

Результаты проверок кэшируются на 30 секунд, чтобы не «пинговать» внешние сервисы на каждом запросе.

В футере отображается **количество запросов за последние 60 минут** и пик запросов в минуту. Служебные опросы (`/health/`, `/helper/api/v1/status_service/`, `/scheduler/status/`, прогресс НК, сам `/monitoring/`) учитываются отдельно и в пользовательскую нагрузку не входят.

## Мониторинг нагрузки

`LoadTrackingMiddleware` измеряет каждый запрос: группу endpoint (`url_name`/`view_name`),
метод, класс статуса, время ответа, время и число запросов к БД, пик параллельных.
Раз в `REQUEST_METRICS_FLUSH_SECONDS` (30 с) минутные агрегаты пишутся в
`app_event.RequestMetric` UPSERT'ом с прибавлением — несколько процессов и рестарты
складываются корректно, история не теряется.

- **Страница `/monitoring/`** (только администратор): RPS по минутам/часам, p95 и
  среднее время ответа, ошибки 5xx, доля медленных запросов (>1 c), время в БД,
  топ-endpoint'ов по количеству и по p95; диапазоны 1 час / 24 часа / 7 дней,
  автообновление раз в 30 с.
- **API `/monitoring/api/metrics/?range=1h|24h|7d`** (админ) — те же данные в JSON.
- **Исходящие вызовы** (`app_event.ExternalCallMetric`): все HTTP-запросы к ЧЗ,
  Нацкаталогу, СУЗ, сервису подписей, заводам и 1С идут через
  `app_helper/external_http.py` и пишут сервис/метод/исход/длительность. В таблице
  «Внешние API» — количество, ошибки, среднее, p95 и максимум по каждому сервису;
  ожидание лимитов True API видно отдельной строкой «Ожидание лимита ЧЗ».
  Проверки доступности (health-панель) помечены сервисом `probe` и в бизнес-ошибки
  не входят.
- **Очередь задач**: готовые/выполняющиеся/завершённые за час, возраст старейшей
  готовой задачи, p95 и максимум длительности, ошибки за час.
- **Инфраструктура** (`app_event.SystemMetric`): CPU/RAM/load/RSS web-процесса
  (Linux `/proc`), активные соединения Postgres, `idle in transaction`,
  `max_connections`, размер БД, транзакции/мин, `temp_bytes`/мин.
- **Health-чеки**: «Внешние API» — доля ошибок по сервисам
  (`EXTERNAL_ERROR_RATE_THRESHOLD`, минимум вызовов `EXTERNAL_MIN_CALLS`);
  «Очередь задач» — порог готовых задач (`QUEUE_MAX_READY`), возраст старейшей
  (`QUEUE_MAX_READY_AGE_SECONDS`) и ошибки за час (`QUEUE_MAX_FAILED_PER_HOUR`);
  «Соединения БД» — доля занятых соединений Postgres (`DB_CONNECTIONS_THRESHOLD`);
  «Нагрузка» — запросы/час (50 000), p95 (`LOAD_P95_THRESHOLD_MS`), доля 5xx
  (`LOAD_ERROR_RATE_THRESHOLD`).
- **История** хранится `REQUEST_METRICS_RETENTION_DAYS` дней (по умолчанию 14) и
  чистится ежедневной задачей `prune_request_metrics` (запросы, внешние вызовы и
  инфраструктура).
- **Live-слой** `app_helper/load_tracker.py` (память процесса) остаётся fallback'ом:
  если таблицы метрик нет, нагрузка считается по нему, и страницы не падают.

### Хранение логов и метрик

| Таблица | Что хранит | По умолчанию | Кто чистит |
| --- | --- | --- | --- |
| `EventLog` | живая лента событий | 90 дней | `cleanup_event_logs` (ежедневно) |
| `HealthCheck` | история health-проверок | 14 дней | `check_system_health` (каждые 5 мин) |
| `UIPStatusLog` | аудит переходов статусов УИП | 365 дней | `cleanup_old_logs` (ежедневно) |
| `DBTaskResult` | завершённые фоновые задачи | 30 дней | `cleanup_old_task_results` (ежедневно) |
| `RequestMetric`, `ExternalCallMetric`, `SystemMetric` | метрики нагрузки | 14 дней | `prune_request_metrics` (ежедневно) |

Проверить объём и очистить вручную:

```bash
python manage.py cleanup_logs            # отчёт: строки, старейшая запись, срок
python manage.py cleanup_logs --cleanup  # удалить устаревшее по всем таблицам
```

Чтобы журнал и логи не разрастались от повторяющихся сбоев:

- `safe_external_call` подавляет одинаковые события `EventLog` (и error-лог)
  на 5 минут — упавший внешний сервис не пишет запись на каждый вызов;
- проверки доступности логируют ошибку не чаще раза в 5 минут на URL;
- панель статусов читает **снимок `HealthCheck`** (воркер обновляет раз в 5 минут),
  а не делает живые проверки на каждом рендере страницы; живая проверка —
  только если истории ещё нет или снимок старше 30 минут;
- `UVICORN_ACCESS_LOG=0` отключает per-request access-log (Docker-логи и так
  ротируются: `json-file`, 10 МБ × 3).

## CI/CD

### GitHub Actions

| Workflow | Файл | Назначение |
| --- | --- | --- |
| CI | `.github/workflows/ci.yml` | При push/PR поднимает PostgreSQL, ставит зависимости и прогоняет `manage.py check`, `makemigrations`, `migrate` (default + archive) и `collectstatic`. |
| Deploy | `.github/workflows/deploy.yml` | `git pull` ветки → `docker compose up --build` → проверки. Запускается вручную (`workflow_dispatch` с выбором ветки) или при push в `main`. |

**Требования для Deploy:** self-hosted runner, установленный на сервере деплоя, с метками
`linux` и `party-management`. Каталог проекта задаётся repository variable `DEPLOY_PATH`
(если не задана — используется workspace раннера). В каталоге должен лежать файл
`config/.env`. Ручной запуск: Actions → Deploy → Run workflow → выбрать ветку.

### Скрипт деплоя

Альтернатива Actions для ручного выката на сервере (Linux — `deploy.sh`, Windows — `deploy.ps1`):

```bash
./deploy.sh [branch] [--check-only] [--no-pull] [--no-build]
```

```powershell
.\deploy.ps1 -Branch main [-CheckOnly] [-NoPull] [-NoBuild]
```

Порядок действий скрипта:

1. `git fetch` / `checkout` / `pull --ff-only` указанной ветки (по умолчанию — текущей);
2. `docker compose build`;
3. запуск БД и ожидание готовности (`healthcheck`);
4. **gate-проверки** (останавливают деплой при ошибке): `manage.py check`,
   `manage.py makemigrations`, `manage.py collectstatic --noinput`;
5. применение миграций: `migrate` и `migrate --database archive`;
6. `docker compose up -d --build` и пост-проверка `manage.py check` в запущенном
   контейнере.

Флаг `--check-only` выполняет только шаги 1–4 (без миграций и запуска) — удобно
использовать как pre-deploy проверку.
